Super chat rollover

One long-running chat that feels like a normal session: streaming, steering, prompt cache. Omnigent decides what the model carries forward, and the agent can still reach every message ever sent. The same shape as Meta Muse and Rakazo.

01 · LIVE

A normal resident session

One native CLI (Claude Code, Codex, Pi) stays running between turns. Streaming, mid-turn steering, prompt cache and tool calls all work as they do upstream.

02 · ROLLOVER

Omnigent owns compaction

When the context gets long, Omnigent writes a summary checkpoint and restarts the CLI from summary + recent messages + memory. Between turns only.

03 · RECALL

The summary is a pointer, not the truth

A read-only tool pages and searches the full record, so "what was my first message?" gets an exact answer.

Blindfold every turn vs rollover

Blindfold (built, strict mode)

  • A new CLI session every turn
  • No streaming, no steering
  • No warm prompt cache
  • A ~60 s web-UI hold on turn 2 and later (open)
  • Strict guarantee: the model never sees more than N messages

Rollover (proposed, super chat)

  • A new CLI session only at rollover
  • Streaming and steering on every turn
  • The cache stays warm between rollovers
  • A fresh session costs about 0.5 s, once per rollover
  • The model sees summary + recent messages; recall fetches the rest exactly

The pieces

Mode switch

The label omnigent.context.mode: unset means upstream (side chats, the default); rollover is the super chat; blindfold is strict mode. Side chats drop the label.

Trigger

Checked after each turn: the tokens since the latest compaction item, plus system text and memory. Real usage is used where the forwarder reports it; otherwise count_tokens. The default threshold is 45% of the model's window, following Muse's 150k of 350k, which leaves room for a heavy tool turn.

Rollover content

A rolling summary (summarize_history over everything since the last checkpoint, merged with the previous summary), plus the last 20 messages with their tool calls, plus memory. All of it is written as one compaction item.

Owning compaction

For rollover sessions, each CLI's own auto-compaction is off at launch. The exact flag for each CLI must be verified against the real CLI first. As a safety net, a CLI-side compaction is detected, the way the Codex forwarder already does.

Recall tool

session_history(action="read", before=<item id>, limit=5)   # page backward · default 5 · max 20
session_history(action="search", query="…", limit=10)          # FTS scoped to this session
session_history(action="status")                                # tokens used · window · left before rollover

Read-only and scoped to the calling session; reading other chats is permission-gated. The tool and the system text carry the rule: "The summary may omit details. When earlier context matters, recover it before answering."

Memory (phase 4)

A small curated memory block injected at every turn and every rollover; memory_search and memory_write (the agent writes before replying); a background writer in observe; provenance on every item; top-5 recall. A time tag is added to each user message.

Phases

1
Rollover for Claude and Codex. Label, trigger, the assembler's compaction item, pane recycle, CLI auto-compaction off. Proof: fill past the threshold → a compaction item is written and the pane relaunches; streaming on every turn; the codeword survives through the summary or recent messages.
2
Recall tool. session_history: read, search, status. Proof: after a rollover, "what was my first message?" is answered word for word through the tool.
3
Pi. Compaction in resume.py, rebuild on rollover, token estimate. Proof: phases 1 and 2 pass on pi-native.
4
Memory. Store, tools, injection, time tag. Proof: a fact from session A is known in a new session.
5
Polish. Background pre-summary, per-turn recall permission, the web UI switch. Proof: a rollover turn takes about as long as a normal one.

Open questions

  • Threshold: 45% of the window (Muse), or a message count (Rakazo: 50 recent, compacting 50 at a time)? Proposal: tokens, with a message cap as a backstop.
  • Summarizer model: the session's own, or a cheap fixed one? Proposal: a cheap one, on the runner's credentials.
  • Blindfold: keep it as the strict mode with no new work? Proposal: yes.
