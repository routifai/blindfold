The standard model in plain words

Every agent memory system separates two things. Short-term memory is what the model sees in the current conversation: its context window. It fills up, so old turns get trimmed or summarized, and a recall tool lets the agent look up exact old messages again. Long-term memory survives across conversations and comes in three kinds:

  • Semantic: facts and preferences about the user ("wants figures in CAD"). Usually split into a small core that is shown every turn and a larger store that is searched when needed.
  • Episodic: things that happened ("on Sep 26 we built the bank deck"), retrieved when a similar situation comes up.
  • Procedural: how the agent should behave. Instructions or skills it rewrites as it learns; this is what "self-improvement" means.

Three choices every system makes

When is memory written?
In the hot path, by the agent calling a tool during the conversation, or in the background, by a separate process that reads the conversation afterwards (Letta calls it a sleep-time agent). The hot path is immediate; the background is more careful and doesn't slow the reply. Muse does both: the agent edits MEMORY.md in the turn, and an upkeep run distills new conversation about once an hour when there is something new.
How is memory read?
Either always in context (a small block injected every turn) or on demand (a search tool). Muse does both: its curated files are injected, and its claims are searched with memory_search.
What happens when a fact changes?
Some systems overwrite: Mem0's model decides ADD, UPDATE, DELETE or NOOP for each new fact. Others keep history: Zep gives every fact a valid-from and valid-to date. Muse keeps history: a new claim supersedes the old one, a repeated one is reinforced, and valid_until retires facts that expire.

Where Muse differs, link by link

Recall: chat never embedded
Letta and Zep put the conversation itself into a vector index or graph. Muse doesn't: old messages are read by paging (chat.read_messages) and keyword search. Only distilled memory gets vectors, so the vector index stays small and clean.
Core: profile rebuilt, not edited
USER.md is regenerated from the claims, and only when it is out of date (a real run reported "projection_already_current"). The claims are the truth; the profile is a view of them, so it can't drift.
Procedural: measured self-improvement
A nightly job reviews what worked and writes a synthesis of how to act for this user, and a daily job turns recurring work into skills. Each change is scored over a time window (calibration_records) and "changes that measurably don't help are retired". Most systems rewrite instructions without checking.
Writing: only verified claims kept
Mem0-style systems store whatever the model extracts. Muse's upkeep run keeps a candidate only if it passes verification. One real run read 106 rows and inserted no claims at all. Muse never revealed the exact verification rule.
Updates: markdown first, database as index
Muse's memory is plain markdown files that the user can read and edit (MEMORY.md, a dated log per day, people pages). The database with its embeddings is only an index over those files. Most systems are database first, with no human-readable source.

Bottom line

Muse is the textbook design built completely: short-term context with compaction and recall, long-term facts, events and behaviour, written both in the turn and in the background, read as an always-shown core plus search. It stands out by being careful about what it writes (a verification gate, history kept, the profile derived from claims) and by checking that its own self-improvement actually helps.
